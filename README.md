# Ускорение Qwen3-VL на Apple M4

Домашнее задание №1 по курсу «Дистилляция и ускорение моделей», ИПИИ НИУ ВШЭ.

В работе исследую локальный инференс **Qwen3-VL-8B-Instruct** на MacBook Air M4 с 24 ГБ объединённой памяти. Сравниваю точность весов и размер изображения по задержке, памяти и качеству ответа.

## 1. Модель и контекст применения

Прикладной сценарий — выбор целевого объекта мобильного робота по изображению и команде пользователя. Например, по команде «найди синий светильник» модель должна выбрать нужный объект. В планируемой постановке объекты заранее обозначены номерами, ответ — номер или none.

Модель не отвечает за управление двигателями, предотвращение столкновений и построение маршрута. Это отдельный модуль понимания команды и сцены. Mac используется как доступная платформа локального прототипа. Результаты на другие бортовые компьютеры автоматически не переносятся.

Режим: inference, online, одно изображение на запрос, batch size 1, один пользователь. Веса загружаются один раз. Цель — p95 полного запроса после прогрева не более 1 секунды при коротком ответе. Это требование выбранного приложения, а не универсальный норматив робототехники.

Пока проверены запуск, производительность на одной фотографии и несколько вопросов к другой сцене. Выбор пронумерованной цели и оценка качества на наборе сцен ещё не реализованы.

Не утверждаю, что исходная модель не поместится при любом входе. BF16 на момент подготовки отчёта не запускалась. Ограниченный запас памяти для неё — риск, а не установленный результат.

Запуск нативный через MLX-VLM с GPU через Metal. Neural Engine специально не используется. При длительной нагрузке пассивное охлаждение может ограничивать производительность, но частоты и температуры в проведённых опытах не измерялись.

## 3. Архитектура

Процессор готовит изображение и разбивает его на патчи. Vision Transformer формирует визуальные признаки. Пространственное объединение патчей сокращает последовательность, проекции приводят признаки к размерности языковой части. DeepStack дополнительно передаёт признаки нескольких уровней ViT в декодер. Языковая часть обрабатывает визуальную информацию вместе с вопросом и последовательно генерирует ответ.

| Блок | Параметры из config.json модели 8B |
|---|---|
| ViT | 27 блоков, hidden size 1152, 16 attention heads |
| Патчи | Пространственный размер 16 × 16, temporal patch size 2 |
| Объединение патчей | Spatial merge 2 × 2 |
| Выход визуальной части | Размерность 4096 |
| DeepStack | Визуальные уровни 8, 16, 24 |
| Языковой декодер | 36 слоёв, hidden size 4096 |
| MLP декодера | Intermediate size 12288, SiLU |
| Attention декодера | 32 query heads, 8 key/value heads, head dim 128 |

Важны два этапа: **prefill**, обработка входной последовательности, и **decode**, генерация выходных токенов. Размер изображения влияет на визуальный энкодер и длину входа декодера. Длина ответа влияет на decode.

## 4. Вычислительные затраты и bottlenecks

| Возможное узкое место | Причина | Что проверено |
|---|---|---|
| Визуальный энкодер | Больше патчей — больше операций attention и MLP | Задержка растёт с размером изображения |
| Prefill декодера | Визуальные токены удлиняют вход | Отдельное время prefill ещё не измерено |
| Веса и линейные слои | Матричные умножения и чтение весов из общей памяти | 4-битный вариант экономнее и быстрее 8-битного на малом входе |
| Decode | Последовательная генерация токенов | В benchmark ответ намеренно короткий |
| Подготовка изображения и Python | Накладные расходы входят в время запроса | Пока не выделены отдельным профилированием |

Общее время не доказывает, что модель именно memory-bound или compute-bound. Это гипотезы для профилирования. Размер исходного изображения также не равен фактическому числу токенов: processor может менять разрешение.

### Методика замеров

Модель загружается один раз, затем выполняются один прогревочный и пять измеряемых запросов. Перед и после измерения вызывается синхронизация MLX. Загрузка учитывается отдельно. Запрос включает чтение и подготовку изображения, вычисления и генерацию ответа. Межзапросный KV-кеш и явный кеш визуальных признаков в скрипте не передаются.

Вопрос: «Name one main object in the image. Answer with a single word.» Температура 0, лимит 8 выходных токенов. Во всех этих сериях ответ был laptop.

**MLX peak** — пик активных выделений памяти, учитываемых MLX, включая модель. Это не полная память процесса и не вся занятая RAM. Его не нужно складывать с памятью Python из Activity Monitor. Swap проверяется отдельно на уровне macOS.

### Точность весов, вход 512 × 384

| Конфигурация | Медиана, с | Диапазон, с | Пик MLX, ГиБ |
|---|---:|---:|---:|
| 4 бита, offline | 1,690 | 1,681–1,695 | 5,930 |
| 8 бит, offline | 1,928 | 1,908–1,968 | 9,744 |

При переходе от 8 к 4 битам задержка сократилась на **12,3%**, память MLX — на **39,1%**. Это сравнение готовых checkpoint. Их правила квантизации по слоям нужно дополнительно сверить; одной метки «4/8 бит» для описания формата недостаточно.

### Разрешение, 4-битная версия

| Изображение | Медиана, с | Диапазон, с | Пик MLX, ГиБ |
|---|---:|---:|---:|
| 512 × 384, исходная серия | 1,705 | 1,693–1,719 | 5,930 |
| 1024 × 768 | 6,167 | 6,147–6,193 | 6,216 |
| 1536 × 1152, повтор | 15,092 | 14,809–15,227 | 6,205 |

Уменьшение входа с 1536 до 512 пикселей по длинной стороне соответствовало примерно 8,9-кратному снижению задержки. Это не гарантированное ускорение на произвольных сценах.

Первая серия 1536 была нестабильной: время выросло с 17,705 до 27,859 с. Причина не установлена. В повторе рост не воспроизвёлся, маленький вход после нагрузки дал медиану 1,696 с. Подтверждённого вывода о thermal throttling нет.

Загрузка около 62 с совпала с переключением VPN. Она не используется как характеристика локального чтения весов. Офлайн-загрузка 4-битной модели заняла 0,936 с.

Таблицы в [results/](results/) восстановлены из выводов терминала, а не являются оригинальными CSV с Mac. Описание происхождения находится в [results/README.md](results/README.md).

## 5. Системные ограничения

Критичны память и задержка отдельного запроса. В последовательном режиме около одной секунды на запрос нужно, чтобы обслуживать один кадр в секунду без постоянного роста очереди. Само p95 ≤ 1 с ещё не гарантирует отсутствие очереди при длительных выбросах.

Планируемые критерии:

- p95 полного запроса после прогрева ≤ 1 с для короткого ответа. Пяти повторов на одной фотографии для проверки недостаточно.
- Работа без OOM и устойчивого роста swap. 24 ГБ — физическое ограничение, отдельный искусственный лимит пока не вводится.
- Непрерывная проверочная серия разных кадров 60 секунд. Это тест задержек и памяти, а не доказательство длительного теплового равновесия.
- Доля правильных целевых объектов и ответов none на размеченных сценах. Предварительно допустимую потерю до 2 процентных пунктов относительно BF16 нужно проверить на достаточно большом наборе. BF16 и эта оценка пока не выполнены.

Обе проверенные конфигурации пока не достигли секунды даже на простом коротком вопросе.

## 6. Гипотезы ускорения

| Метод | Что меняется и почему может помочь | Ограничения |
|---|---|---|
| Квантизация весов | Меньше памяти и трафика чтения весов; эффект на малом входе измерен | Зависимость от вычислительных ядер; активации не становятся автоматически 4-битными; возможная потеря качества |
| Бюджет визуального входа | Меньше патчей и токенов, ниже стоимость ViT и prefill | Потеря мелких объектов и деталей; нужно измерить токены и качество |
| Короткий формат ответа | Номер цели вместо описания сокращает decode | Оптимизация сценария, не сжатие весов |
| Выбор кадров при изменении сцены | Меньше вызовов на почти одинаковых кадрах | Снижает нагрузку, но не обязательно время отдельного запроса; возможен пропуск события |

Основные методы — квантизация и бюджет визуальных токенов. Pruning и дистилляция в текущий эксперимент не входят. Неструктурированное удаление весов без специальных sparse kernels не обещает ускорения. Дистилляция потребовала бы ученика и обучения, что расширяет объём работы.

## 7. Инженерные компромиссы

4-битная версия экономит память, но качество нельзя считать сохранённым по одному ответу laptop. На фотографии комнаты обе версии верно отвечали ABOVE на короткий вопрос о полке над зеркалом. В длинном описании обе ошибочно относили полку к отражению. У 4-битной версии в одном ответе также появились повторения. Это отдельные наблюдения, не статистическое доказательство преимущества 8 бит.

Уменьшение изображения ускоряет обработку, но может ухудшать чтение номеров, поиск мелких предметов и различение похожих объектов. Готовые MLX checkpoint упрощают запуск, но добавляют зависимость от конвертации и версий библиотек. BF16 может дать ориентир качества, но требует больше памяти.

### Сделано

- Запущены готовые 4- и 8-битные версии на GPU M4.
- Выполнены предварительные замеры разрядности и разрешения.
- Найдены примеры корректных ответов и ошибок понимания сцены.

### Дальнейшие шаги

1. Проверить BF16 на малом входе без изменения системных лимитов Metal.
2. Зафиксировать ревизии checkpoint, настройки квантизации и фактическое число визуальных токенов.
3. Подготовить независимые размеченные сцены с номерами объектов.
4. Сравнить качество и p95 на общем наборе, провести минутную серию.
5. Если секунды достичь не получится без большой потери качества, описать полученный предел платформы.

## Воспроизведение

Нужны Mac с Apple Silicon и Python 3.12. Веса скачиваются из Hugging Face отдельно.

~~~bash
python3.12 -m venv .venv
source .venv/bin/activate
python -m pip install -r requirements.txt
python prepare_images.py /path/to/photo.jpg --output-dir data
python -u benchmark.py --image data/test-512.jpg --output results/local-4bit-512.csv
python -u benchmark.py --model mlx-community/Qwen3-VL-8B-Instruct-8bit --image data/test-512.jpg --output results/local-8bit-512.csv
~~~

После первого скачивания:

~~~bash
HF_HUB_OFFLINE=1 python -u benchmark.py --image data/test-512.jpg --output results/local-4bit-offline.csv
~~~

Для будущего BF16-эксперимента используется модель mlx-community/Qwen3-VL-8B-Instruct-bf16. При красном давлении памяти, быстром росте swap и ухудшении отзывчивости эксперимент следует остановить, записав условия.

requirements.txt фиксирует основные версии, но это не полный lock-файл. Для новых измерений сохранить:

~~~bash
python -m pip freeze > requirements-lock.txt
~~~

CSV дополняется JSON с параметрами и версиями. Исторические замеры выполнены более ранним вариантом того же скрипта. Личные фотографии не публикуются, поэтому буквально повторить исторические числа без исходных кадров нельзя. На других фотографиях значения и ответы будут отличаться.
